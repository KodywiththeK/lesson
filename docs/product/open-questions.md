# 확인 필요 질문

이 문서의 항목은 사용자 확인 전 최종 정책으로 구현하지 않는다. 단, 질문에 막히지 않는 순수 로직, UI 골격, 테스트 하네스는 진행할 수 있다.

## 제품/테넌트

- 서비스의 실제 제품명은 무엇으로 할지?
- 사용자가 처음 가입하면 학원을 직접 생성하는지, 초대 링크로 학원에 합류하는지?
- 한 사용자가 여러 학원에 소속될 수 있는지?
- 한 선생님이 여러 학원에 동시에 소속될 수 있는지?
- 더 클래식은 초기 seed/reference tenant로만 둘지, 첫 운영 학원으로 실제 데이터 migration을 할지?

## 조직과 역할

- 데스크 직원 역할은 모든 학원에서 기본 제공할지, 학원별로 켜고 끄는 옵션인지?
- 선생님은 모바일, PC, 둘 다 어느 환경을 우선 지원해야 하는지?
- 선생님이 학원 피아노 수업 출석을 직접 확인할 수 있는지, 배정된 개인레슨만 확인할 수 있는지?
- 선생님이 개인레슨을 직접 등록할 수 있는지, 원장/데스크만 등록할 수 있는지?
- 선생님에게 원생 보호자 연락처를 노출할지?

## 권한과 민감정보

- 데스크 직원이 수입/지출 화면 일부에 접근할 수 있는지?
- 선생님은 세후 급여만 볼지, 기본 급여와 세후 급여를 모두 볼지?
- 주민등록번호를 v1에서 저장할지?
- 주민등록번호를 저장한다면 누가 볼 수 있고, 마스킹/보관/삭제/audit 정책은 어떻게 할지?
- 현재 도메인 구현은 답변 전 보수적 임시 모델로 원문 주민등록번호를 저장하지 않고 `encryptedValueRef + maskedValue`만 기록한다. 실제 암호화 방식과 접근 권한은 DB/Supabase 저장 phase 전에 확정해야 한다.
- audit log를 원장에게 화면으로 노출할지?

## 레슨과 일정

- 학원 피아노 수업의 유효 요일은 무엇인지? PDF에는 월~금 기준 표현과 토요일 예시가 함께 보인다.

## 2026-10-15 spec-review에서 추가된 질문

임시 결정은 사용자가 정한 것이며 최종 정책 확정 전까지 유지한다.

- **삭제 방식(임시 결정)**: 퇴원 원생·퇴사 선생님의 삭제 버튼은 비활성이고 보관만 허용한다. 현재 삭제 RPC는 출석, 회차권, 교재 판매, 지급된 급여 정산까지 연쇄 삭제(cascade)한다. 정식 정책(hard/soft delete, 연쇄 범위, 30일 후 자동 처리, 복구 UI)을 정해야 한다. 거래처·회차권·교재 출고·개인레슨·학원 일정의 삭제 허용 여부와 사유 입력도 함께 정한다.
- **잔여 0 출석**: 회차권 잔여가 0인 원생이 실제로 등원했을 때 출석을 막을지(현재), 기록은 허용하고 마이너스/미정산으로 표시할지.
- **만료 기준일**: 회차권 만료를 수업 날짜로 볼지 출석 처리일로 볼지(현재 수업 날짜). 만료 후 재등록은 병합할지 새로 만들지, 병합 시 유효 시작일을 덮어써도 되는지.
- **차감 정정**: 출석을 결석으로 정정하면 회차가 사유 없이 자동 복구되고 이력이 남지 않는다. 사유 입력, 이력 보관(복구 취소 표시), audit 기록이 필요한지.
- **미래 날짜 출석**: 미래 수업에 출석 처리를 허용할지, 과거 수업은 며칠까지 허용할지.
- **0원 회차권**: 서비스·이월 회차권(결제 금액 0원)을 허용할지(현재 폼은 거부).
- **재등록 병합**: 같은 원생·악기의 재등록을 한 회차권에 병합할지(현재), 구매 단위별로 유지해 결제 이력을 보존할지.
- **휴원/퇴원 시 개인레슨**: 원생이 휴원·퇴원하면 예정된 개인레슨을 자동 취소할지(현재 정기 학원 일정만 취소).
- **개인레슨 수정·취소**: 이동·취소·삭제를 허용할지, 출석 이후 취소하면 회차를 복구할지 막을지. 시간 충돌을 막을지 경고만 할지, 같은 원생·선생님의 학원 수업과의 겹침도 대상인지.
- **자동 생성 원장 행**: 수강료·교재·회차권·급여로 자동 기록된 입출금을 수정·삭제할 수 있는지.
- **교재 재고·결제 완료**: 교재 등록·재고·입고일·자동 가격·출고 시 재고 부족 허용 여부, 결제 대기 건을 결제 완료로 바꾸는 권한과 화면.
- **미수금 범위**: 미수금 현황에 수강료 미납만 넣을지, 교재 결제 대기와 회차권 결제까지 포함할지.
- **teacher·desk 권한 반영**: `allowDeskFinance`/`allowDeskTicketAdjustment` 플래그를 실제로 연결할지, teacher의 학원 출석·개인레슨 등록·본인 급여(`/my/payroll` 화면)를 허용할지. 현재 teacher의 "내 급여" 링크는 화면이 없어 숨겼다.
- **원생 수정 폼 범위**: 등록 폼과 같은 필드(등록일, 나이, 학년, 학교, 직업, 연락처, 복수 악기, 요일별 시간, 할인 구분)를 수정할 수 있게 할지. 수정 RPC(스키마) 변경이 필요하다.
- **페이지네이션 방식**: 지금은 전체를 한 번 조회해 브라우저에서 자른다. 데이터가 커지면 서버 페이지네이션이 필요하고, 그때 DB collation이 한글 가나다순을 보장하는지 확인해야 한다.
- **오류 문구 위치**: 영문 RPC 예외를 DB 메시지에서 한글화할지, 지금처럼 클라이언트에서 변환할지.
- **데모 계정**: `owner@lesson.local` 계정이 원격 DB에 남아 있는지 확인하고 운영 DB라면 제거한다(로그인 폼 기본값은 이미 제거).
- **급여 대상 범위**: 선생님 월급 화면은 재직 선생님만 계산한다. 이번 달 중 퇴사·휴직한 선생님의 미지급 급여 행, 지난달 지급 이력을 계속 보여줄지 정해야 한다.
- **삭제 RPC 회수(스키마, 사용자 승인 필요)**: `delete_withdrawn_student`·`delete_resigned_teacher` RPC는 owner/desk가 직접 호출하면 연쇄 삭제가 가능하다. 화면에서는 삭제를 막았지만 DB는 열려 있으므로, 정책이 정해지기 전까지 두 RPC를 revoke하거나 연결 기록이 있으면 거부하는 migration이 필요하다.
- **대량 데이터 한도**: 목록·급여 원천(`lesson_events`)·원장(`ledger_entries`)은 범위·페이지 조건 없는 단일 조회라 서버 `max_rows`(로컬 1000)에서 조용히 잘릴 수 있다. 원격 설정을 확인하고 금액 집계는 월 범위 조회·서버 집계로 옮길지 정한다.
- **급여 지급 금액 재계산**: 지급 확정은 브라우저가 계산한 금액을 RPC로 보낸다. 서버에서 재계산·대조할지 정한다(스키마 영향).
