# 원생 수업 시간과 구매 건별 회차권 검증 증거

## 발견과 계획

- 연결 요구사항: 2026-10-28 사용자 확정 계획의 30분·직접 입력 수업 시간, 원생별 예약 가능·실제 잔여 표시, 구매별 독립 회차권과 일정의 권별 회차 번호. 인수 기준은 `docs/product/acceptance-scenarios.md`, 추적 관계는 `docs/product/traceability-matrix.md`에 반영했다.
- 기존 회차권 등록은 학원·원생·악기별로 한 권에 구매를 합쳤다. 수업 시간은 화면과 DB 검증 모두 40·60분에 묶여 있었다. 기존 데이터의 합쳐진 권은 분할하지 않고 한 권으로 보존한다.
- 가독성: 구매 권 선택·권별 가용량·회차 표시를 각각 이름이 있는 함수와 필드로 표현한다.
- 예측 가능성: 서비스권 우선, 같은 종류의 오래된 유효권 우선, 출석 때만 실제 차감, 결석의 예약 해제, 기간 밖 이동 거부를 DB 경계에 둔다.
- 응집도: 회차 회계와 동시 요청 잠금은 migration의 함수에, 수업 길이·금액 검증은 원생 도메인과 DB 입력 검증에 둔다.
- 결합도: 새 구매만 독립 권으로 만들고 이전 통합권의 잔액·일정 이력을 유지한다. 데모 데이터의 구매 ID와 실제 RPC의 역할을 분리한다.
- simplify 목표: 중복 원생 가용량 조회와 기존 권 병합 분기를 없애고, 화면의 회차 번호는 저장된 권별 값을 우선 사용한다.

## Red → Green → Refactor

- 30분·45분·240분 종료 시각, 5~240분 정수 범위, 수동 레슨비, 원생 선택지의 두 횟수, 기존 `3/4`와 새 `0/4`, 권별 회차 표시, 데모 권 ID 중복을 먼저 실패 테스트로 확인했다.
- 전체 회귀의 첫 실행에서는 기존 화면 테스트가 새 원생 선택 문구와 독립된 구매 행을 기대하지 않아 실패했다. 기대값을 현재 정책으로 갱신했다.
- 최종 검토에서 **원생 등록·수정 RPC가 여전히 40·60분만 허용**하는 누락을 발견했다. SQL 계약 테스트를 먼저 실패시킨 뒤 새 migration에서 RPC 검증을 5~240분 정수와 30분·직접 입력의 양수 레슨비로 확장했다. 데모 일반 구매의 0원 허용과 삭제 후 구매 ID 충돌, 원래 권이 삭제된 결석의 취소 우회도 실패 테스트로 확인한 뒤 고쳤다. 마지막 점검에서는 직접 입력으로 40분을 적으면 입력칸이 닫히는 현상과 삭제 일정이 기존 권의 회차 번호를 밀어내는 이관 오류를 각각 실패 테스트로 재현하고 수정했다.
- Refactor에서 신규 구매의 병합 분기를 제거하고, 원생 선택지의 가용량 조회를 항목당 한 번으로 줄였다. 수업 시간 선택은 외부에서 기본값으로 되돌릴 때 직접 입력 칸이 닫히도록 단일 파생 조건을 사용한다.

## 데이터와 적용 상태

- `supabase/migrations/20261028055929_purchase_scoped_lesson_tickets.sql`은 수업 시간 제약·RPC, 구매별 권의 고유 제약 제거, 일정의 권·회차 필드, 기존 일정·정산 출석 연결, 권별 예약·출석·정산·결석 취소·서비스 회수 검사를 담는다. 서비스·유료 구매의 감사 이력과 기존 RLS 경계를 유지한다.
- 과거에 이미 합쳐진 권을 임의로 분할하지 않는다. 권과 연결할 수 없는 **예정 일반 일정**이 있으면 migration을 중단하고, 기존 초과 예약은 그대로 표시한다.
- 적용 전 원격 점검에서 연결 불가능한 예정 일정·등록 횟수 불일치·잘못된 잔여는 모두 0건이었다. 원격 PostgreSQL은 17.6이며 필요한 기존 제약·함수 시그니처와 RLS를 확인했다.
- 첫 MCP 적용은 기존 `private_lesson_reservation_guard`가 이관 `UPDATE`를 막아 실패했다. 직후 원격 migration history와 새 컬럼을 확인해 **부분 반영 0건**을 확인했다. 격리 DB에 기존 트리거를 추가해 동일 실패를 재현하고, 이관 중 해당 트리거만 잠시 비활성화했다가 다시 켜도록 수정했다.
- 수정한 migration을 Supabase MCP `apply_migration`으로 원격 프로젝트 `zkzqmqtzzlgljkuctpbn`에 적용했다. 원격 history 버전은 `20261028055929`이며 선행 `20261027144316` 뒤에 기록됐다. 의존 순서가 유지되므로 로컬 파일명도 원격 버전에 맞췄다.
- 적용 후 읽기 전용 SQL에서 신규 `lesson_events` 컬럼 3개, FK 1개, 인덱스 2개, 5~240분 CHECK, 기존 권 유일 제약 제거, 이관되지 않은 예정 일반 일정 0건, 번호가 없는 예정 일반 일정 0건, 번호가 붙은 삭제 일정 0건, 일정 보호 트리거 활성화를 확인했다. 대상 public 테이블의 RLS와 `authenticated` 조회·RPC 실행권, `anon`의 RPC 실행 거부, 내부 권 선택 함수의 직접 실행 거부도 확인했다.
- 실제 원장 권한 문맥에서 서비스 4회권과 유료 4회권을 연속 등록해 서로 다른 권 ID·`merged=false`를 확인한 뒤 PL/pgSQL 예외 하위 트랜잭션으로 모두 롤백했다. grant 총건수는 적용 전과 같은 11건이다. 원장 가용량 조회는 성공했고 비인증 조회는 거부됐다. 활성 선생님 계정이 없어 선생님 역할의 실제 JWT 경로는 재현하지 못했다.

## Consolidate와 남은 위험

- 가독성: 구매·예약·사용의 의미가 함수명과 권별 필드로 구분되고, 30분·직접 입력의 수동 금액 안내가 명확하다.
- 예측 가능성: 기존 권의 번호와 잔액은 재구매로 바뀌지 않으며, 출석과 결석의 실제 차감 규칙을 격리 DB에서 확인했다.
- 응집도: 권별 선택·가용량·차감은 DB 함수 안에서 같은 범위로 검사하고, 화면은 서버가 반환한 횟수를 표시한다.
- 결합도: 이전 통합권은 유지하고 신규 권만 독립적으로 만든다. 온보딩 변경과 다른 기능의 코드는 수정하지 않았다.
- simplify 결과: 병합 결과 분기와 중복 조회를 제거했다. 변경 파일을 다시 읽고 수업 시간 RPC 누락, 데모 ID 충돌, 직접 입력 40분 UI, 삭제 일정 번호 이관을 보완했다. 저장소의 `/simplify` 지침에 따라 Claude Code CLI를 호출했으나 해당 CLI가 `Not logged in`으로 종료됐다. 동일한 재사용·단순화·효율·추상화 기준을 직접 검토했다.
- 남은 위험: 실제 두 세션 동시 등록, 선생님·데스크 브라우저 로그인 경로, 환불과 출석 취소의 전체 원격 RPC 연결은 검증하지 못했다. 격리 DB는 함수 경로를 확인했지만 실제 운영 데이터의 모든 조합을 재현하지는 않는다. Supabase Performance Advisor의 새 FK 미색인 정보 1건은 `(ticket_grant_id, starts_at)` 인덱스가 실제 권별 조회·삭제 경로를 지원하지만 복합 FK의 `academy_id`가 선두에 없어 advisor가 감지한 것으로, 같은 열의 중복 인덱스를 추가하지 않았다. Security Advisor 경고는 적용 전후 동일했다.
