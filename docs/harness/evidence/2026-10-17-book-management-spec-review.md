## Supabase 증거

- Migration: `20261019090000_book_stock_schema.sql`(컬럼·병합 이행·FK·권한), `20261019090100_book_stock_rpcs.sql`(RPC 8개·내부 함수 3개·옛 7인자 삭제). **2026-10-17 운영 DB 적용 완료**(집계 사전 확인: 교재 2·출고 2·입고 이력 2·중복 0 → dry-run → push, 원격 history 일치).
- 적용 후 카탈로그 확인(읽기 전용): 새 시그니처만 존재(오버로드 없음), anon 실행 불가·내부 함수는 앱 사용자 실행 불가, `books`·`book_releases`는 authenticated SELECT만, 새 FK·check·인덱스 존재, 교재 `title_key` 채움·재고 0·출고 수량 1 이전.
- RLS·역할별 확인: 계약 테스트(SQL 문자열)와 카탈로그 확인까지. 재고 잠금·동시성, 결제 취소의 원장 삭제, 데스크 거부는 실제 계정으로 확인하지 못했고 병합 이행은 중복 데이터가 없어 실행되지 않았다. 확인 항목은 `supabase-migration-runbook.md`의 교재 관리 절.

## 품질 정리

- 코드 단순화: 옛 `book-purchase-list-screen`(단일 표)을 탭별 화면으로 분리·삭제, 재고 변경·원장 행 생성을 SQL 내부 함수 한 곳으로 모음, 무효화를 `invalidateAfterBookChange` 한 곳으로, 출고·결제 완료 화면이 같이 쓰는 파일을 중립 이름(`book-format.ts`, `book-supabase.ts`)으로 정리.
- 재사용한 추상화: `fetchAllRows`, `buildListView`(정렬 옵션), `PaymentDialog`(검증·안내 콜백 prop으로 일반화), 공통 목록 컨트롤, 상담 삭제 확인 선례, 기존 재원생 선택지 쿼리.
- 가독성: 규칙·문구는 `book-stock.ts`의 `BOOK_MESSAGES`와 한계 상수 한 곳, 화면은 책임별 파일(폼·표·다이얼로그·화면).
- 예측 가능성: 서버·도메인·데모가 같은 오류 문구를 쓰고, 데모 mutation은 규칙 위반을 동기 오류로 던져 운영 경로와 같은 흐름이다. 결제 완료·대기 상태별 허용 동작을 명세 표로 고정.
- 응집도: 재고·출고 데모 규칙은 `academy-demo-books.ts`, 재고 규칙은 도메인 순수 함수.
- 결합도: PaymentDialog는 도메인 지식 없이 콜백만 받음, 화면은 동작 prop 주입, 서버 문구와 클라이언트 문구는 계약 테스트·도메인 상수로 일치 확인.
- simplify 결과: 두 화면의 Supabase client 상태 중복 제거, `useMemo` 제거, 리뷰 지적 사항 반영.
- 남긴 Warning: `book_inventory_batches` 미사용 표 유지, 서버 RPC가 합산 여부를 응답하지 않아 화면이 사전 미리보기·권수 비교로 추정, 원생 연결이 끊긴 대기 출고는 수정 시 원생을 다시 골라야 저장됨(서버는 null 유지 허용), 화면 파일은 모두 300줄 미만(가장 큰 테스트 파일은 `book-stock-screen.test.tsx` 630줄).
