# 휴일 배정·할인·결제 방식·정산 문자 검증 기록

## 발견과 계획

정기 일정 생성은 시간표 외에도 원생 변경·보강 추천에서 호출되고 급여의 정규 수업 분모에 사용된다. 공휴일 자료가 없을 때 기존 일정을 읽으면서 신규 자동 배정을 보류하고, 자동 제외와 출결을 구분하기 위해 DB 경계에 정책·검증된 자료·제외 표시를 둔다. 수강료와 급여는 기존 원장·스냅샷과 같은 트랜잭션 및 학원 범위 잠금을 사용한다. 요구사항과 인수 시나리오는 기능 명세 및 추적표의 해당 항목에 연결했다.

## Red → Green

- 쉬는 날 설정, 미확인 공휴일, 공식 응답 불완전·다른 월 오류, 자동 제외의 숨김 집계, 다음 달 보강 추천 보류를 테스트했다. 각 신규 구현의 핵심 테스트에서 의도한 실패를 확인하고 구현했다.
- 결제 방식 선택과 저장·취소, 할인 변경 경고, 급여 금액·학생별 상세, 문자 템플릿과 복사 실패를 테스트했다. 기존 수강료의 할인 출처가 불명확한 경우 현재 월에도 추정해 바꾸지 않는 별도 격리 DB 실패를 확인하고 수정했다.
- 최신 원격 스키마를 읽기 전용으로 확인해 사용한 원천 테이블·컬럼을 대조했다. 원격 migration history의 마지막 적용은 `20261028055929`이며 이전의 `20261028073720_lesson_ticket_cancellation_history.sql`도 미적용이다. 신규 다섯 파일은 이 뒤에 순서대로 적용해야 한다.

## Verify

- `pnpm test:run`: 227개 파일, 2,261개 테스트 통과.
- `pnpm typecheck`, `pnpm exec tsc --noEmit`, `pnpm lint`, `git diff --check`: 통과.
- `pnpm test:e2e`: 41개 통과. 기존 회차권 탭의 오래된 선택자를 실제 접근성 이름에 맞게 수정했다. 새 휴일 설정의 데스크톱·320px 모바일, 모바일 정산 문자 다이얼로그를 확인하고 별도 2개 테스트를 재실행했다. 화면 캡처를 열어 배치와 내용도 확인했다.
- 격리 PGlite에서 간이 테이블과 RPC를 사용해 공휴일 자동 제외·출결 보존과 차단·중복 휴원·수강 종료 시 복원 방지·24시간 경과·공식 저장 권한, 결제 방식과 입금 취소, 불명확한 할인 보호와 소개 할인 변경, 급여 총액 검증·다른 선생님의 분모·상세 보존·직접 쓰기 제한을 실행했다. 이는 실제 전체 스키마에서의 migration 재생이나 실제 역할별 RLS 및 다중 세션 경합 검증을 대체하지 않는다.
- 독립 검토에서는 공통 일정 생성 경계, 출결과 제외 경합, 비율제 서버 재계산, 금전 데이터의 직접 쓰기 우회를 발견했다. 공통 잠금·상태 재확인·직접 쓰기 권한 회수와 안내를 반영했다. 에이전트 실행 한도로 최종 독립 재검토는 책임자가 이어서 수행했다.

## Quality Consolidation

- **가독성:** 휴일 정책, 급여 자료 준비, 정산 문자 렌더링을 각 경계의 함수와 컴포넌트로 나누고 실패 안내를 해당 화면에 붙였다.
- **예측 가능성:** 자동 제외와 수동 취소를 별도 표시로 구분하고, 자료가 없으면 기존 조회를 유지하되 신규 배정과 불완전한 급여 확정을 보류한다. 템플릿 저장·삭제 및 복사 실패 시 내용을 보존한다.
- **응집도:** 급여는 기존 도메인 계산 기준을 재사용하고 지급 원장·상세는 DB 트랜잭션에서 함께 처리한다. 할인 변경도 원생 저장과 같은 트랜잭션에서 처리한다.
- **결합도:** 휴일 준비는 급여 화면 조회에 한정하고 다른 수입 화면은 기다리지 않는다. 결제 방식 필드는 공용 입금 창에서 필요한 경우에만 켠다.
- **simplify 결과:** 월별 공휴일 준비 함수를 분리하고 휴일 설정·추천 재시도를 해당 화면에 두었다. 학생별 상세 포맷을 지급 전후에 공유하고 실제 검증이 필요한 분기만 유지했다. 추측성 최적화는 적용하지 않았다.

## 남은 위험과 적용 조건

- 원격 DB에는 아무 migration도 적용하지 않았고 커밋·push도 하지 않았다. 앱은 새 DB 컬럼·RPC에 의존하므로 DB 적용 전 배포하면 안 된다.
- 로컬에서 Docker/Postgres 서버를 사용할 수 없어 전체 기존 migration 순차 재생, 실제 역할별 RLS, 다중 세션 경합은 검증하지 못했다. 학원 단위 잠금과 기존 행 잠금 순서가 경쟁 시 교착 상태로 트랜잭션을 중단시킬 가능성은 실제 PostgreSQL 다중 세션에서 확인해야 한다. 간이 PGlite 검증 결과를 전체 DB 검증으로 간주하지 않는다.
- 서버 환경에 `KASI_HOLIDAY_API_KEY`와 승인받은 `SUPABASE_SERVICE_ROLE_KEY` 설정이 필요하다. 값은 브라우저에 노출하지 않는다. 설정·배포 방법은 `docs/engineering/supabase-setup.md`에 기록했다.
- `next-env.d.ts`는 작업 시작 전 사용자 변경 내용과 바이트 단위로 일치하게 유지했다.

## 커밋 전 재검토 (2026-10-30)

- 세 독립 검토에서 행 잠금 후 학원 advisory 잠금 대기에 따른 교착 가능성, 미확정 급여 문자, 템플릿 삭제 중 중복 요청 및 긴 미리보기의 모바일 넘침을 확인했다. 학원 잠금은 경합 시 즉시 재시도를 안내하도록 바꾸고 출결 가드도 행 잠금 전에 같은 방식을 사용한다. 미지급 급여가 미준비 또는 설정 오류이면 문자 작성도 막고, 지급 완료 문자는 그대로 연다. 삭제 중 중복 요청과 미리보기 줄바꿈을 보완했다.
- 별도 임시 PostgreSQL 18에서 두 세션을 사용해 일정 행 선잠금과 학원 잠금의 역순 경합, 출결 가드 경합이 즉시 실패·롤백되고 대기 행 잠금이 해제되는지 확인했다. 경합한 다른 작업은 사용자가 다시 시도해야 한다. 별도 간이 스키마에서 다섯 신규 migration의 기본 SQL 동작도 PostgreSQL로 재실행했다. 전체 Supabase 스키마 순차 재생과 모든 쓰기 경로의 동시성 검증은 아직 수행하지 못했다.
- 재검토 후 `pnpm test:run` 227개 파일·2,266개 테스트, `pnpm typecheck`, `pnpm lint`, `pnpm test:e2e` 41개가 통과했다. 기존 `next-env.d.ts`는 테스트 전 상태로 복원했다.
- **운영 적용 전 확인 필요:** 기존 앱의 수강료 입금은 세 인자 RPC를 사용하지만 신규 DB는 네 인자 RPC를 요구한다. 또한 기본으로 켜진 공휴일 정책은 신규 서버가 검증한 공휴일 자료를 기록하기 전 해당 월의 신규 정기 배정을 보류한다. 따라서 새 서버 환경의 `SUPABASE_SERVICE_ROLE_KEY` 설정과 앱 배포를 확인하지 않고 DB만 먼저 적용하면 기존 운영 기능이 영향을 받는다. 이전의 `20261028073720` migration도 원격에 미적용이라 범위와 순서를 확인해야 한다.
- **simplify 결과:** 검토 지적은 동작 경계를 명확히 하는 최소 수정으로 처리했다. 중복되는 잠금 검사는 변경 중인 migration별 독립 적용 순서와 권한을 유지하기 위해 별도의 범용 함수로 옮기지 않았다. 금액 출처가 불명확한 기존 수강료는 현재 월도 추측하지 않고 안내하며, 과거 잔액을 임의로 재분배하지 않는다.
