## Supabase 증거

- Migration: 5개를 사용자 요청으로 원격 운영 DB에 적용했다(`db push --dry-run`으로 대상 5개 확인 후 `db push --yes`, 원격 history 일치). 적용 후 카탈로그 확인과 앱에서 확인할 항목은 `supabase-migration-runbook.md`의 같은 날짜 절에 있다.
- 검증 방법: 저장소에 DB 실행 테스트가 없어, 임시 하네스(스크래치 디렉터리, 저장소에 넣지 않음)에서 pglite로 최소 스키마 스텁 위에 실제 migration SQL을 실행했다. 이는 실제 원격 스키마가 아니므로 적용 후 재확인이 필요하다.
- 하네스가 발견한 결함: 원장 쓰기 트리거에서 `app.ledger_rpc` 설정이 없으면 `current_setting`이 NULL이라 조건 전체가 NULL이 되어 **데스크의 직접 수입 행 쓰기를 막지 못했다**. `coalesce(…, '')`로 고치고 계약 테스트에 고정했다. 감액 루프에서 UPDATE 뒤 DELETE 조건을 평가해 행이 잘못 지워지는 순서 결함도 DELETE 먼저로 고쳤다. 문자열 계약 테스트만으로는 둘 다 잡히지 않았다.
- 역할별 확인(하네스): 데스크는 규정 변경 불가, 데스크 등록의 결제 수입 행 생성 가능, 데스크 직접 수입 행 쓰기·수정 차단, 선생님은 등록·미리보기·교재·거래처 삭제 불가. RLS 정책 자체는 스텁에서 슈퍼유저로 실행해 확인하지 못했다.
- 환불 동작: 언제든 비례(100,000원×3/10=30,000원)·반 이하 경계·환불 불가, 두 번 결제한 회차권은 최근 결제부터 감액(80,000→70,000, 20,000 행 삭제), 전액 환불 시 수입 행 삭제, 반올림(33,333), 잘못 등록은 사용 기록이 있으면 거부.

## 품질 정리

- 코드 단순화: 환불 판정·잘못 등록 판단을 `private.lesson_ticket_refund_context` 한 곳으로 모아 미리보기와 삭제가 같은 값을 쓴다. 수입 행은 두 방식 모두 등록 이력의 `ledger_entry_id`로 찾는다(데모와 같다). 미리보기 타입은 환불 견적 + 잘못 등록 가능 여부로 합쳤고, 데모의 죽은 분기와 이중 매핑을 없앴다. 설정 저장 후 재조회 대신 `setQueryData`, 미리보기 쿼리는 창이 열려 있는 동안 재조회하지 않는다. 사용 이력 조회용 인덱스 `lesson_ticket_usages_grant_idx` 추가.
- 재사용한 추상화: `SectionCard`/`SectionHeader`, `ListStatusAlert`, `toUserMessage`, AlertDialog·RadioGroup, `queryKeys`, 기존 RPC·API 모듈 구조.
- 테스트 정리: 표 셀 단언은 role·`data-label` 기준, 클래스 단언 없음. e2e 로케이터는 exact로 좁혀 의도를 드러냈다.
- 가독성: 환불 규칙은 UI 밖 순수 함수(`lesson-ticket-refund.ts`)와 한국어 주석으로 설명한다. SQL 헤더에 규칙·보안 검토 항목을 적었다.
- 예측 가능성: 삭제 확인창이 서버가 계산한 값만 보여 주고 결과 토스트가 실제 금액을 알린다. 환불 불가·미사용 아님 같은 경우를 확인창에서 먼저 안내한다. 기본 규정은 환불 불가.
- 응집도: 규정 이름·옵션·경계(`usedCount*2 <= total`)를 도메인 모듈 한 곳에서 정하고 설정 화면·확인창·데모가 공유한다.
- 결합도: 데스크 결제 입력은 기능 키 `ticket-payment-input`으로 분리해 화면은 `canRecordPayment` 불리언만 받는다. 원장 트리거 예외는 회차권 RPC·`source='lesson-ticket'`·원장/데스크 세 조건이 모두 맞을 때만 열린다.
- simplify 결과: 4개 관점(재사용·단순화·효율·altitude)으로 검토해 위 항목을 반영했다. **반영하지 않은 항목(사유)**: 삭제 확인창 공용화(`ConfirmDeleteDialog`)와 라디오 카드 공용화(저장소에 이미 5개 이상 복제되어 별도 정리 과제, 이번 범위 밖), Supabase 클라이언트 상태 보일러플레이트 공용화(기존 9개 화면과 같은 관례), 금액 포맷 함수 통합(기존 3곳 중복 정리는 별도), 원장 트리거를 소스별 허용표로 일반화(현재 사용처가 회차권 하나뿐), 도메인 환불 함수와 SQL의 공유 표 기반 대조 테스트(후속 과제), 정책 값 목록 이중 선언, 불필요 export 정리.
- 코드 품질 리뷰: Critical 없음.
- 남긴 Warning/Suggestion: 위 미반영 항목.
- 남은 부채: DB 실행 테스트(pgTAP 등)가 저장소에 없다. 도메인 TS와 SQL 환불 계산은 손으로 맞춘 두 구현이라 규칙을 바꿀 때 둘 다 고쳐야 한다.

## 위험과 확인 질문

- 위험
  - 데스크가 수입 행을 만들고 고치는 경로가 처음 생겼다(회차권 출처 한정). 보안 검토 필요(`permissions.md`).
  - 환불 처리로 지운 회차권은 사용 이력·조정 이력이 cascade로 사라지고 확정 출석 기록만 남는다.
  - 확인창의 환불 예정 금액은 참고용이다. 열어 둔 사이 규정이나 잔여가 바뀌면 실제 금액이 달라질 수 있고 결과 토스트가 실제 금액을 알린다(확인 금액 고정이 필요하면 별도 결정).
  - 감액은 최근 결제부터 거꾸로 적용한다(여러 번 결제한 경우). 사용자는 "환불액만큼 줄임"까지만 정했고 배분 방식은 구현 결정이다.
  - 연결된 수입 행이 없는 등록(원장이 직접 지운 경우)은 감액할 행이 없어 환불액만큼 줄지 않을 수 있다.
  - 교재 쪽 결제 입력(`/books/shipments`)은 여전히 `role === "owner"` 직접 비교다.
- 후속 질문: 환불 이력 화면이 필요한지, 확정 출석 기록을 환불 삭제 뒤 어떻게 볼지(`open-questions.md`).
