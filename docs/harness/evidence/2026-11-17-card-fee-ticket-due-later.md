# 2026-11-17 카드 수수료 자동 기록 · 회차권 납입일 미정

## 요약

- 목표: 학원 추가 피드백 두 건을 처리한다.
  1. 학원 고정 수입을 카드로 입금 처리하면 입출입내역에 자동 기록되는 문제
  2. 회차권 등록 때 납입일을 나중에 적고 싶다는 요청
- 본질 확인: 1번은 "카드는 자동 기록을 없애 달라"는 요청이었다. 사용자와 확인한 실제 문제는 따로 있었다. 카드 매출은 며칠 뒤 카드사가 수수료를 떼고 입금하므로, 결제액 전액으로 기록하면 입출입내역이 통장과 맞지 않는다. 자동 기록은 유지하기로 했다. 대신 카드사별 수수료율을 설정해 두고 수수료 출금을 함께 기록한다(사용자 선택).
- 완료한 변경
  - 카드 수수료
    - DB: `card_fee_rates` 표와 원장 전용 저장·보관 RPC를 추가했다.
    - 연결 칸: `ledger_entries.fee_for_entry_id`로 수수료 행을 수입 행에 붙였다. 같은 학원끼리만 붙고, 수입 행이 지워지면 cascade로 함께 지워진다. 수입 금액이 바뀌면 비례 조정 trigger가 수수료를 맞춘다.
    - 분류: `카드 수수료`(`card-fee`) 분류를 추가했다.
    - 입금 RPC: 6인자 입금 RPC 두 개(수강료·회차권)를 추가했다. 옛 4인자 RPC는 그대로 둔다.
    - 입금 창: 카드사 선택과 수수료 미리보기·수정 칸을 넣었다.
    - 화면: 설정에 `카드 수수료` 화면과 메뉴를 추가했다. 데모도 대응했다.
  - 회차권 납입일 미정
    - DB: `due_on`의 not null을 해제했다. 10인자 등록 RPC는 `p_due_on = null`이면 미정으로 남긴다. `set_lesson_ticket_due_on` RPC를 추가했다.
    - 등록 폼: `등록일과 동일`·`직접 입력`·`나중에 입력` 라디오를 둔다.
    - 입금 상태 칸: `납입일 미정` 표시와 `납입일 입력`/`납입일 수정` 버튼을 추가했다.
    - 수입 관리: 납입일이 없으면 등록일 달부터 이월하고, 정렬 기준일(`billedOn`)을 등록일로 둔다.
  - 작업 브랜치: `main`으로 전환해 작업했다.
- 커버한 요구사항: `functional-spec.md`의 회차권 입금 상태와 수입 관리 결제 방식, `acceptance-scenarios.md`의 "카드 수수료·회차권 납입일 미정 (2026-11-17)", `decision-log.md`의 2026-11-17 두 건.

## Supabase 증거

- Migration: `20261117000000_card_fee.sql`, `20261117000100_lesson_ticket_due_on_later.sql`
  - 로컬 DB에는 psql로 직접 적용했다.
  - 로컬 DB에는 `feat/platform-admin` 브랜치의 `20261115*` migration이 이미 있었다. 그 위에서도 문제없이 적용됐다.
  - 운영 DB(2026-11-17): CLI `db push --remote=<ref> --dry-run`으로 대상이 이 2건뿐임을 확인한 뒤 적용했다. 적용 후 원격 이력 75건으로 로컬 파일 수와 같고 마지막 버전은 `20261117000100`이다. 읽기 전용 조회로 `card_fee_rates` RLS 켜짐, `ledger_entries.fee_for_entry_id` 칸, 분류 check의 `card-fee`, 수수료 비례 트리거, `lesson_ticket_grants.due_on` null 허용, RPC(`save_card_fee_rate`/4, `archive_card_fee_rate`/2, 입금 RPC 4·6인자, `set_lesson_ticket_due_on`/3)를 확인했다.
- 역할별 시나리오(원장·데스크 JWT로 확인)
  1. 카드사가 없으면 카드 입금에 수입 행 1건만 생긴다.
  2. 같은 이름의 카드사(공백·대소문자 무시)와 소수 셋째 자리 수수료율은 거부한다.
  3. 카드사가 있는데 카드 입금에서 고르지 않으면 `카드사를 선택해 주세요.`로 거부한다. 현금 입금에 카드사를 넘기면 `카드 결제에만…`으로 거부한다.
  4. 수강료 150,000원을 카드로 입금하면 수수료 2,175원(1.45%)이 `source=tuition`, `category=card-fee`로 수입 행에 연결된다. 입금 취소하면 두 행이 모두 삭제된다.
  5. 수수료를 2,000원으로 직접 입력하면 그대로 저장된다. 원장이 수입을 150,000원에서 75,000원으로 정정하면 수수료가 1,000원이 된다.
  6. 데스크가 회차권을 납입일 미정으로 등록하면 `due_on`이 null이다. 데스크가 납입일 입력 RPC를 호출하면 2026-11-20으로 저장된다. 입금 뒤에는 변경이 거부된다.
  7. 데스크 카드 입금
     - 수수료 2,900원이 `source=lesson-ticket`으로 생긴다. 원장 가드를 통과한다.
     - 입금 취소하면 두 행이 삭제된다.
     - 전액 환불하면 수입이 삭제되고 수수료도 cascade로 지워진다.
     - 잘못 등록 취소에서도 수수료가 함께 지워진다.
  8. 데스크 RPC 문맥(`app.ledger_rpc`)에서 수입을 100,000원에서 40,000원으로 바꾸면 수수료가 1,450원에서 580원이 된다. 설정 없이 데스크가 직접 갱신하면 `수입 관리 권한이 없습니다.`로 거부한다.
  9. 데스크는 카드사를 읽을 수 있고, 저장하면 거부된다.
  10. 옛 9인자 등록은 지금처럼 납입일을 등록일로 저장한다.
- 플랫폼 관리자 영향(`platform-admin-plan.md` 9절)
  - 새 표 `card_fee_rates`는 `academies`에 `on delete cascade`로 붙어 있어 학원 영구 삭제 때 함께 지워진다.

## 품질 정리

- 코드 단순화
  - 회차권 입금 변경 안내 문구가 목록과 수입 관리에 따로 있었다. 이를 도메인의 `LESSON_TICKET_PAYMENT_CHANGE_MESSAGES` 하나로 합쳤다.
  - 수수료 되돌리기는 FK cascade와 비례 trigger로 처리했다. 그래서 기존 입금 취소·환불·취소 RPC는 고치지 않았다.
- 재사용한 추상화
  - 날짜 입력: 기존 `PaymentDialog`에 `initialDate`만 더해 납입일 입력에도 썼다.
  - 다른 기존 패턴
    - 원장 RPC: `teacher_message_templates`
    - 입금 RPC 래핑: `20261030020909`
    - 회차권 원장 가드: `app.ledger_rpc`
- 가독성: 카드 수수료 규칙(계산, 선택 필요 여부, 금액 검증, 비례 조정)을 `src/domain/card-fee.ts` 한 곳에 모았다. 각 함수 주석에 서버의 같은 규칙 위치를 적었다.
- 예측 가능성
  - 납입일 값은 세 가지로 구분한다.
    - `undefined`: 상태 도입 전 자료라 등록일과 같다.
    - `null`: 미정이다.
    - 문자열: 그 날짜다.
  - 이 해석을 `getLessonTicketDueOn` 하나로 통일했다.
  - 등록 API도 같은 규칙이다. 납입일을 생략하면 등록일, `null`이면 미정으로 보낸다.
  - 수수료가 수입을 따라간다는 규칙은 migration 주석과 기능 명세에 적었다.
- 응집도: 수수료 행의 생애주기는 수입 행에 붙어 DB에서 함께 움직인다. 화면은 카드사 선택과 금액만 넘긴다.
- 결합도: 입금 창은 카드사 목록과 금액을 prop으로만 받는다. 조회는 화면이 하고, 데모·테스트에서는 `cardFeeRatesQueryOptions`로 바꿔 넣을 수 있다.
- simplify 결과: 재사용·품질·효율 세 관점을 독립 에이전트에 병렬로 맡겼다. 발견 사항은 직접 코드에서 확인해 아래처럼 반영했다.
- 반영한 것
  - 수수료 입력은 다른 금액 입력과 같은 `parseWonInput`으로 읽는다(쉼표 허용, "1e3" 거부). 범위 검사는 `getCardFeeAmountRangeError` 하나로 두어 입금 창과 데모가 같이 쓴다.
  - 데모의 카드사 필요 여부는 `needsCardFeeChoice`로 판단한다.
  - RPC 수수료 인자는 `toCardFeeRpcParams` 하나로 묶어 수강료·회차권 API가 같이 쓴다.
  - 카드사 이름 길이는 `CARD_FEE_NAME_MAX_LENGTH`를 쓴다.
  - 데모 입출입내역의 수정·삭제도 수수료를 따라가게 했다(`syncCardFeesWithIncome`). 서버의 cascade·trigger와 같다.
  - 입출입내역 삭제 확인 문구에 "카드 수수료 출금도 함께 지워진다"를 넣었다.
  - 카드사 목록을 읽는 중이거나 읽지 못했으면 카드 입금 확인을 막고 안내한다. 이전에는 이 상태가 카드사 없음처럼 보여 서버 거부만 받았다(테스트 추가).
  - 회차권 응답 매핑에서 `due_on`을 그대로 둔다. null은 미정, 칸이 없으면 `getLessonTicketDueOn`이 등록일로 해석한다.
  - `save_card_fee_rate`에서 동시에 같은 이름을 저장하면 unique 위반이 나는데, 이를 한국어 안내로 바꿔 준다. 로컬 DB에서 다시 컴파일하고 시나리오를 재실행했다.
- 효율 검토에서는 고칠 것이 없었다. 같은 쿼리 키를 공유하고, `fee_for_entry_id` 부분 인덱스가 있으며, trigger가 재귀하지 않는다.
- 남긴 Warning
  - 두 화면이 카드사 목록을 읽는 방식이 다르다. 회차권 목록은 직접 만든 client로 읽고, 수입 관리는 페이지가 넘겨준다. 각 화면이 원래 Supabase client를 얻는 방식이 달라서 그대로 두었다.
  - `formatWon`은 features 폴더에 있어 입금 창에서 재사용하지 않았다.
  - 수수료 비례 조정은 이미 반올림한 수수료에서 다시 계산한다. 그래서 부분 환불을 여러 번 하면 1원 단위 오차가 누적될 수 있다(회차권 환불은 한 번에 끝나서 실제로는 한 번만 일어난다). 원장 화면은 자동 기록 행의 유형을 바꿀 수 없어, 수입을 출금으로 바꿔 수수료가 떨어지는 경우는 UI로는 생기지 않는다.
  - 옛 4인자 입금 RPC가 남아 있어, 직접 호출하면 서버의 카드사 필수 검사를 건너뛸 수 있다. 배포 전환이 끝나면 4인자 RPC를 지우는 후속 migration이 필요하다(runbook에 적음).
  - `database.types.ts`는 이전부터 오래된 상태이고 이번 칸·표도 없다. 운영 적용 뒤 다시 생성하는 것이 좋다.
  - 납입일 입력에 `PaymentDialog`를 쓰고 있어, 이름이 "입금"인 점은 어색하다. 날짜 하나와 확인을 받는 범용 다이얼로그로 쓰고 있다.

## 위험과 확인 질문

- 실제 정산 수수료가 설정한 율과 다를 수 있다. 원장이 입출입내역에서 수수료 행을 고칠 수 있다.
- 수수료는 입금일에 기록한다. 실제 카드사 입금일은 며칠 뒤라 달이 다를 수 있는데, 이번 범위에서는 받아들인다.
- 기존 카드 입금 건에는 소급하지 않는다.
- 원장이 입출입내역에서 카드 입금의 수입 금액을 고치면 수수료도 같은 비율로 바뀐다. 의도한 규칙이며 명세에 적었다.
- 운영 적용 순서: migration → 앱 배포. 옛 앱은 옛 4인자 RPC를 쓰므로 적용 직후에도 동작한다.
