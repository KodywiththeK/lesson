## 먼저 작성한 테스트와 Red

- 리드 작업: 등록 다이얼로그(모듈 없음), 메뉴·권한(5개 테스트 파일 갱신 후 실패 확인), 휴원·퇴원 migration 계약(파일 없음 → ENOENT), 수정 폼(5건 실패), 요일 정렬(1건), 상태 화면 삭제 안내(1건), 거래처 페이지 순회(2건), 선생님 명단 도메인·API·화면·migration 계약, 선생님 원생 페이지(1건), 레슨 워크스페이스 선생님 경로(1건).
- 에이전트 작업: 각 보고에 도메인·API·화면 테스트의 Red를 확인했다고 적었다. **Red를 확인하지 못한 항목**: 선생님·급여 에이전트의 migration 계약 테스트(migration을 먼저 쓰고 계약을 나중에 씀, 대신 PGlite로 SQL 동작을 임시 검증), `teacher-salary-form-state` 첫 실행(파일 위치 문제로 "No test files"), 가격표 에이전트의 `hasSameStudentName`(사후 확인), 상담 에이전트의 `toConsultationFormValues` 보강. 리드의 `teacher-payroll-contract`의 "급여 형태 선택" 계약 1건도 SQL을 먼저 고친 뒤 테스트를 추가했다.

## Supabase 증거

- Migration 7개: `20261018080000`(휴퇴원·수정), `090000`(시급 재계산), `090100`(급여 원장 전용), `090200`(주민번호), `100000`(상담), `110000`(가격표·할인·나이), `120000`(선생님 명단). **2026-10-17 운영 DB 적용 완료**(`db push --dry-run` 후 `--yes`, 원격 history가 로컬 파일명과 일치). 적용 전 리드가 리뷰 범위 밖이던 `110000`을 직접 읽었다.
- 적용 후 카탈로그 확인(읽기 전용): 오버로드 정리, anon 실행 불가·service_role 전용 함수, Vault `teacher_rrn_key` 존재, pg_cron 2개 활성, 정책·컬럼·트리거 존재, 기존 나이 3건 backfill. 자세한 목록은 runbook.
- RLS·역할별 확인: SQL 문자열 계약 테스트까지만. 선생님·급여 에이전트가 PGlite stub으로 시급 재계산·급여 인자 거부·주민번호 왕복·직접 쓰기 트리거를 임시 확인했으나 저장소에 포함하지 않았고 실제 Supabase(RLS, Vault, `auth.uid`)에서는 확인하지 못했다.
- 적용 후 반드시 확인: Vault 키 존재, `cron.job` 등록, 오버로드 정리, 선생님 계정 화면 동작(runbook 표).

## 품질 정리

- 코드 단순화: 선생님 화면 1159줄 → 4개 파일, 원생 등록·수정 폼을 `student-registration-dialog`·`student-edit-form`·`student-weekly-schedule-fields`·`student-lesson-fee-fields`로 분리, 죽은 도메인 모듈·API 제거, 쓰지 않게 된 시급 등원 시간 필드 제거, 중복 `toSeoulDate` 통일.
- 재사용한 추상화: `fetchAllRows`(거래처·상담), `paginateItems`·`buildListView`(정렬 옵션 추가), `StudentRegistrationDialog`(상담 연동), 공통 목록 컨트롤·표 규칙.
- 가독성: 가격표·구간·할인은 `lesson-pricing.ts` 상수 한 곳, 마스킹·검증·분 계산은 도메인 순수 함수. 중첩 삼항을 쓰지 않았다.
- 예측 가능성: 가격표가 없는 조합은 임의 금액 대신 직접 입력 상태와 이유 문구, 서버 RPC는 영어 예외 대신 한국어 문구, 부분 성공(번호 저장 실패, 수정 두 RPC 중 하나 실패, 상담 삭제 실패)은 구분된 안내.
- 응집도: 시급 계산 규칙은 `teacher-work-minutes.ts`와 SQL에 같은 규칙으로 있고 서로 주석으로 가리킨다(한쪽을 바꾸면 다른 쪽도 바꿔야 함). 등록·수정 폼이 레슨비 입력을 공유한다.
- 결합도: 상담이 원생 폼에 의존하는 곳은 `StudentRegistrationDialog` 하나, 선생님 화면은 `isOwner` boolean, 선생님 원생 화면은 별도 컴포넌트.
- simplify 결과: 에이전트가 각자 분리·중복 제거를 했고, 리드는 리뷰 지적 사항과 요일 입력 공통화를 반영했다. 남은 큰 파일: `student-list-screen.tsx` 1133줄, `students.ts` 1033줄, `teachers.ts` 671줄(분할 후보).
- 남긴 Warning: queryKey에 정렬을 덧붙이는 방식(`createStudentListQueryKey`, 정식 `queryKeys` 확장 대기), 데모 상태가 새 필드(주민번호, 할인 종류 등)를 무시, 선생님 검색에서 급여 형태가 데스크에게도 검색됨, 상담 화면의 동명이인 경고 없음, students 표 컬럼(나이·학교·출석 코드)이 담당 선생님에게 여전히 읽힘.
