# 품질 정리

구현과 검증 후, 작업 완료를 선언하기 전에 반드시 실행한다. 이 단계는 “동작한다”를 “유지보수 가능하다”로 바꾸는 마지막 점검이다.

코드 품질 기준은 `docs/engineering/code-quality.md`를 SSOT로 삼는다.

## production code 검토

변경한 코드를 다음 기준으로 평가한다.

- **가독성**: 한 번에 고려해야 할 맥락이 적고, 복잡한 조건과 매직 값에 이름이 붙었는가?
- **예측 가능성**: 이름, 파라미터, 반환 타입만 보고 동작과 side effect를 예상할 수 있는가?
- **응집도**: 함께 수정되는 코드, 상수, 타입, 폼 검증, 도메인 규칙이 가까이 있는가?
- **결합도**: 공통화와 props 전달이 변경 영향 범위를 불필요하게 넓히지 않는가?
- **경계**: UI 컴포넌트가 도메인 모듈이나 server action에 있어야 할 비즈니스 규칙을 들고 있지 않은가?

## 코드 품질 리뷰 형식

변경 diff를 다음 등급으로 자체 리뷰한다.

- **Critical**: 운영 버그, 권한/tenant 누락, 데이터 손상, 심각한 테스트 공백, 수정 범위를 예측하기 어려운 결합
- **Warning**: 읽기 어려운 조건/분기, 이름과 다른 동작, 숨은 side effect, 성급한 공통화, 함께 바뀌는 코드의 분산
- **Suggestion**: 더 나은 이름, 더 가까운 파일 배치, 작은 helper 추출, 테스트 설명 개선

Critical은 완료 전 수정한다. Warning은 가능하면 수정하고, 남기는 경우 evidence에 이유를 적는다. Suggestion은 현재 작업 범위에서 효과가 분명할 때만 반영한다.

## test code 검토

테스트를 개발 보조물이 아니라 장기 회귀 방지 자산으로 정리한다.

- 사용자에게 보이는 동작 또는 안정적인 도메인 규칙을 표현하는 테스트를 남긴다.
- 임시 구조, incidental class name, 구현 세부사항만 검증하는 테스트는 제거하거나 다시 작성한다.
- UI 테스트는 접근 가능한 role, label, visible text를 우선한다.
- 숨은 전역 상태보다 결정적인 fixture를 사용한다.
- 각 테스트는 독립 실행 가능해야 한다.
- 테스트 이름은 실패했을 때 깨진 요구사항을 설명해야 한다.

## 재검증

품질 정리 후 다음을 수행한다.

- 영향 받은 테스트를 다시 실행한다.
- 공유 코드가 바뀌었으면 더 넓은 검증을 실행한다.
- evidence에 두 번째 검증 결과를 기록한다.
- 코드 품질 리뷰 결과와 남긴 Warning/Suggestion을 evidence에 기록한다.

## 완료 규칙

품질 정리가 완료되었거나 적용 불가 사유가 명시되지 않으면 작업은 완료가 아니다.
