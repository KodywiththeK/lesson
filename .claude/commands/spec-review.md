# 명세 검토·보완 팀 작업

대상 명세: $ARGUMENTS

이 커맨드는 이 프로젝트의 하네스(`AGENTS.md`)를 그대로 따른다. 한 에이전트가 혼자 하지 않고 **역할별 에이전트가 각자 조사 → 리드가 취합 → 개선** 순서로 진행한다. 모든 문서와 사용자 보고는 한국어로 쓴다.

`$ARGUMENTS`에 `--검토만`이 있으면 3단계(취합 보고)까지만 하고 멈춘다. 없으면 질문이 필요한 항목만 사용자에게 묻고 나머지는 개선까지 진행한다.

## 0단계. 준비 (리드가 직접)

1. `AGENTS.md`, `docs/engineering/code-quality.md`, `docs/engineering/shadcn-component-guide.md`, `docs/engineering/design-system.md`, `docs/product/open-questions.md`를 읽는다.
2. 명세가 파일 경로면 읽고, 텍스트면 그대로 쓴다. 명세와 관련된 화면·도메인·API·테스트 파일을 `rg`로 찾아 **범위 목록**(파일 경로)을 만든다. 관련 `docs/product/` 문서와 `docs/harness/evidence/` 선례도 찾는다.
3. 명세가 모호하거나 제품 정책(권한, 급여·결제 해석, 데이터 삭제 방식 등)에 걸리면 조사 전에 먼저 질문한다.

## 1단계. 역할별 병렬 조사 (Agent 도구, 한 메시지에서 동시에)

아래 조사관을 **한 번에 병렬로** 띄운다(`Explore` 또는 `general-purpose`). 조사관은 모두 **읽기 전용**이며 파일을 수정하지 않는다. 명세에 따라 불필요한 역할은 줄여도 되지만 역할을 합치지는 않는다.

각 조사관 프롬프트에는 다음을 반드시 넣는다. 조사관은 이 프롬프트만 보고 일한다.
- 명세 원문과 범위 목록, 먼저 읽을 문서(`AGENTS.md`, 해당 엔지니어링 문서, 관련 제품 문서)
- 맡은 역할의 점검 항목
- 리드의 가설이나 결론은 넣지 않는다(확증 편향 방지). 코드와 명세만 준다.
- 보고 형식: 발견마다 `ID / 등급(Critical·Warning·Suggestion) / 근거(파일:줄) / 문제 / 제안 / 수정 크기(작음·큼) / 정책 질문 필요 여부`. 확인하지 못한 것은 "미확인"으로 적고 추측하지 않는다.

| 역할 | 점검 항목 |
| --- | --- |
| A. 명세 적합성 | 명세 항목별 구현 여부를 표로 판정(일치/어긋남/누락). 인수 시나리오(`docs/product/acceptance-scenarios.md`)·추적 매트릭스와 대조. 테스트가 명세를 실제로 검증하는지. |
| B. CRUD·데이터 완결성 | create가 있으면 수정·삭제도 있는가(삭제는 확인 다이얼로그·보관 정책). **등록 폼의 모든 필드가 수정 폼에도 있는가**를 필드 단위로 비교. 목록·상세·API adapter·query 무효화 일관성, 학원(tenant) scope, 권한별 노출, 읽기 전용으로 확인 가능한 RLS 계약. |
| C. UX·기본값·화면 간결성 | 문맥으로 정해지는 기본값(예: 피아노 레슨 원생이면 담당 선생님 기본값이 피아노 선생님), 입력 단계 축소, 자동 채움, 키보드·모바일(320px) 사용성. 꼭 필요한 기능만 컴팩트한가, **중복된 버튼·기능·정보**가 없는가, 정보 우선순위. 가능하면 dev/demo 화면을 실제 브라우저로 데스크톱·모바일에서 확인. |
| D. 메시지·검증·엣지 케이스 | 에러·validation 메시지가 개발자 말투(`permission denied`, 영어 원문, 내부 코드)가 아닌 **사용자 관점으로 무엇이 문제이고 어떻게 하면 되는지**를 알려주는가. 빈 값·중복·시간 충돌·경계값, 로딩·오류·빈 목록 상태, 접근 가능한 label, 실패 후 재시도, 중복 제출 방지. |
| E. 코드 품질·simplify | `code-quality.md` 4기준(가독성·예측 가능성·응집도·결합도) 기준 리뷰. 비대한 파일·컴포넌트, 중복, 불필요한 props, UI와 도메인 로직 혼재, shadcn 우선 규칙 위반(raw HTML 입력, 브라우저 기본 날짜 입력), 테스트의 구현 세부 의존·누락. |
| F. 정책·재무·권한 리스크 (명세가 돈·급여·권한·삭제·스키마를 건드릴 때만) | 원장 일관성, 트랜잭션 경계, audit, 권한 판단이 UI에만 있는지, 파괴적 동작. **결정은 하지 말고 질문 목록만** 만든다. |
| G. 문서 정합성 (명세·동작이 `docs/`와 어긋날 때) | `functional-spec`, `acceptance-scenarios`, `traceability-matrix`, `open-questions`, 엔지니어링 문서가 현재 구현과 명세에 맞는지. 이미 지워졌거나 옮겨진 파일을 증거로 인용하는 행, 문서에는 있는데 구현에 없는 약속(예: 메뉴 설명과 실제 기능 불일치)을 찾는다. 수정은 하지 않고 목록만 만든다. |

## 2단계. 취합 (리드가 직접)

1. 모든 보고를 모아 중복을 합치고, 서로 충돌하는 제안은 근거를 비교해 조정한다. 조사관이 근거 없이 주장한 항목은 리드가 코드를 직접 열어 확인한다.
2. 각 항목을 분류한다.
   - **즉시 수정**: 정책 결정이 필요 없고 영향이 작거나 명확한 것(누락된 수정·삭제, 수정 폼 필드 누락, 친절하지 않은 메시지, 기본값, 중복 제거, simplify).
   - **질문 필요**: 제품 정책, 권한, 급여·결제 해석, 스키마, 삭제 방식, 큰 UX 흐름 변경.
   - **제안·보류**: 효과가 불분명하거나 범위가 큰 것. 이유를 적는다.
3. 사용자에게 통합 보고를 한다: 명세 적합성 표, 분류별 발견 목록(등급·근거), 질문 목록. `--검토만`이면 여기서 끝낸다.
4. 질문 필요 항목은 `AskUserQuestion`으로 한 번에 묻는다. 답을 기다리는 동안 질문과 무관한 즉시 수정은 먼저 진행해도 된다.

## 3단계. 개선 (TDD, 하네스 절차)

1. 즉시 수정 항목을 **같은 파일을 건드리는 묶음**으로 나눈다. 같은 파일을 여러 에이전트가 동시에 수정하지 않는다. 공유 컴포넌트·도메인 함수·`src/components/ui/`는 리드가 소유한다.
2. 묶음이 서로 다른 파일 집합이고 독립적이면 구현 에이전트를 병렬로 띄울 수 있다(필요하면 `isolation: "worktree"`). 아니면 리드가 순차로 진행한다. 구현 에이전트 프롬프트에는 담당 파일 목록, 실패 테스트부터 쓸 것, 범위 밖 수정 금지, 보고 형식을 넣는다.
3. 각 묶음은 **Red(의도한 이유로 실패 확인) → Green(최소 구현) → Refactor** 순서다. 기존 테스트를 약화하지 않는다. 같은 실패가 3회 반복되면 접근을 멈추고 원인을 정리해 새 전략을 택하거나 질문한다(`docs/harness/failure-policy.md`).
4. 코드 식별자는 원문을 유지하되 사용자에게 보이는 문구와 문서는 한국어로 쓴다. 에러 메시지는 "무엇이 문제 → 어떻게 하면 되는지" 형태로 쓴다.

## 4단계. 독립 재검토와 simplify

1. 변경 diff만 새 리뷰 에이전트(`feature-dev:code-reviewer` 또는 `general-purpose`)에게 준다. 리드의 결론은 주지 않고 `code-quality.md` 4기준과 회귀 위험을 보게 한다.
2. 리드가 변경 파일을 다시 읽고 중복, 불명확한 이름, 숨은 side effect, 불필요한 props를 simplify한다. Critical은 완료 전 수정하고 Warning을 남기면 이유를 evidence에 적는다.

## 5단계. 검증

1. 관련 테스트 → `pnpm typecheck` → `pnpm lint` → `pnpm test:run --reporter=dot` → `pnpm test:e2e`(내부에서 데모 빌드를 한다). 변경 후 simplify까지 끝난 뒤 한 번 더 실행한다.
2. UI가 바뀌었으면 데스크톱과 모바일(320px) 브라우저에서 확인하고, jsdom으로 못 잡는 겹침·레이어·넘침을 본다.

## 6단계. 문서 갱신과 evidence

작업이 끝나면 **코드만 고치고 끝내지 말고** 아래 문서를 현재 구현과 결정에 맞게 갱신한다. 해당 없는 문서는 건너뛰되 evidence에 "변경 없음"으로 적는다. 모두 한국어로 쓰고 `AGENTS.md`의 문서 규칙을 따른다.

| 문서 | 갱신 기준 |
| --- | --- |
| `docs/product/functional-spec.md` | 바뀐 화면 동작·공통 규칙·기본값을 명세 문장으로 반영(구현 세부가 아니라 사용자가 보는 동작). |
| `docs/product/acceptance-scenarios.md` | 새로 보장하는 동작을 Given/When/Then 시나리오로 추가하거나 기존 시나리오를 수정. |
| `docs/product/traceability-matrix.md` | 새·변경 요구사항 행에 테스트와 구현 파일을 연결. 삭제·이동한 파일을 인용하는 행을 정리. 운영 경로 검증이 계약 테스트까지인 경우 그 한계를 적는다. |
| `docs/product/open-questions.md` | 조사 중 나온 미확정 정책 질문을 추가하고, 사용자가 답했거나 임시로 정한 항목은 결정 내용과 날짜를 표시. |
| `docs/engineering/*` (`code-quality`, `shadcn-component-guide`, `design-system`, `permissions`, `testing-strategy` 등) | 새 공통 컴포넌트·규칙·패턴, UX 원칙, 권한 가드 성격(UX용인지 보안 경계인지)을 해당 문서에 간결히 추가. 기존 문장과 중복하지 않는다. |
| `docs/harness/decision-log.md` | 되돌리기 어려운 결정(삭제 정책, 적용 범위, 정렬 예외 등)과 변경 조건을 한 줄씩 기록. |
| `docs/harness/evidence/YYYY-MM-DD-<주제>.md` | `docs/harness/evidence-template.md` 형식. 조사관별 핵심 발견, 반영한 것·보류한 것·질문한 것, Red 테스트와 초기 실패, 검증 명령과 결과, 브라우저 증거, `가독성`, `예측 가능성`, `응집도`, `결합도`, `simplify 결과`, 남은 Warning과 후속 질문. |

갱신 후에는 `rg`로 삭제한 파일명·옛 동작을 설명하는 문장이 `docs/`에 남아 있지 않은지 확인하고, 문서가 가리키는 파일 경로가 실제로 존재하는지 점검한다.

커밋과 push는 하지 않는다. 사용자가 요청하면 논리 단위로 나눠 `type(scope): 한국어 요약`으로 커밋한다.

## 운영 시 주의 (과거 사고 방지)

- 일반 `pnpm build`는 E2E용 데모 빌드(`NEXT_PUBLIC_E2E_DEMO=1`)를 덮어쓴다. E2E 전에는 `pnpm test:e2e`만 쓴다.
- 서버나 프로세스를 정리할 때 `pkill -f`로 패턴 종료하지 않는다. 사용자가 `127.0.0.1:3108`에 띄워 둔 dev 서버가 함께 종료된 적이 있다. 내가 띄운 프로세스만 `lsof -ti :<포트>`로 PID를 확인해 종료한다.
- 생성물(`next-env.d.ts`, `test-results`, `.next`)과 `.env*.local`은 커밋하지 않는다. 검증 후 `git status`로 의도치 않은 변경을 확인한다.
- 실제 Supabase migration 적용, 데이터 삭제, 새 의존성 추가는 사용자 승인 없이 하지 않는다.
